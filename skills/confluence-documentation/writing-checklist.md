# Pre-publication checklist

## Purpose and structure
- [ ] The first lines say what the page is for and who it is for.
- [ ] One page type; the structure follows its template; no empty sections.
- [ ] Headings describe content or tasks; long pages have a table of contents.
- [ ] It does not duplicate another page: existing pages were searched; overlaps are merged or linked.

## Accuracy
- [ ] Every technical statement matches the current code, configuration or system (with its source noted); versions are explicit.
- [ ] Commands and examples are correct and copyable; those not executed are marked as not verified.
- [ ] Unknowns are marked `TBD (who)`, not guessed.
- [ ] Links work and point to stable targets (tags or commits for code, ticket keys, dashboards).

## Usability
- [ ] A reader from the target audience can complete the task with this page alone (runbooks: someone who does not know the system).
- [ ] Procedures have prerequisites, numbered steps, expected results, verification and rollback.
- [ ] Terms specific to the domain or the bank are defined or linked to the glossary.
- [ ] Written in the space's language, with consistent terminology.

## Safety
- [ ] No secrets, tokens, passwords, private keys or connection strings with credentials.
- [ ] No personal or customer data, no production data samples; examples use fictitious values.
- [ ] Internal details (hostnames, IPs, security controls) only to the extent the audience and the space permissions justify.
- [ ] Sensitive pages (incidents, security designs) are placed in a restricted space or page.

## Maintenance
- [ ] Page properties: owner, status, last review date.
- [ ] Labels following the space's conventions.
- [ ] For an update: a version comment summarising the change.
